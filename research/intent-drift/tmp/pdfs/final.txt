                 1. INTRODUCTION AND LITERATURE REVIEW
Large language models (LLMs) transform text into tokens - subword units produced by a tokenizer -
and predict a sequence of output tokens using transformer-based attention [1], [2]. Tokens are therefore
both computational units and billing units. Two systems may answer the same request with different
token counts because of tokenizer design, hidden reasoning, prompt construction, context handling and
response length. A useful comparison must consequently measure task success together with input
tokens, output tokens, latency, cost and safety behavior rather than reporting accuracy alone.

Existing work provides strong foundations but leaves a practical gap. HELM advocates scenario
coverage and multiple metrics [3]. MT-Bench and Chatbot Arena show the value of preference
evaluation while documenting position, verbosity and self-enhancement biases in LLM judges [4].
LiveBench addresses contamination with frequently refreshed, objectively scored questions [5]. These
approaches are valuable, yet public leaderboards can still be unlike everyday student and developer
work, and a single aggregate rank can hide task-specific trade-offs.

Research Aim
The project aims to design and pilot a transparent, user-centric benchmark for comparing accessible
LLMs and AI products on realistic tasks, token efficiency, optimization response, guardrail behavior
and policy compliance. The benchmark will publish prompts, rubrics, settings, raw outputs and
uncertainty so that results can be reproduced and interpreted rather than treated as a single universal
ranking.

Objectives
 - Create a balanced task suite covering knowledge work, coding, reasoning, multilingual use, long
    context and safety-sensitive requests.
 - Measure quality, factuality, instruction adherence, robustness, latency, token use, estimated cost, safe
    refusal and over-refusal.

            2. PROBLEM STATEMENT AND FEASIBILITY STUDY
Problem Statement
Model providers and benchmarking platforms often use different prompt sets, judge models, sampling
settings and reporting rules. Static prompts may be contaminated by training data; subjective judges
may favor verbosity or their own model family; and product interfaces may silently add system
prompts, retrieval, tools or safety filters. Hence, a leaderboard score may not predict which system is
most effective, economical and safe for a real user's task. The research problem is to construct a fair
comparison that exposes these confounders and reports task-level trade-offs.

Research Questions
 - RQ1: How strongly do quality, latency, token consumption and cost vary across models for the same
    real-life task?
 - RQ2: Do rankings change across task categories, languages, context lengths and native products
    versus controlled APIs?
 - RQ3: Which prompt and context optimizations reduce tokens without materially reducing task
    success?
 - RQ4: How do guardrails affect harmful-compliance rate, appropriate refusal, over-refusal and
    usefulness of safe alternatives?
 - RQ5: How stable are results across repeated runs and small meaning-preserving prompt variations?

Proposed Model and Product Scope
The pilot will include only systems for which exact, dated identifiers and lawful access are available.
Candidate families are Anthropic Claude (Opus, Fable and Sonnet variants), OpenAI ChatGPT/API or
Codex-served variants (including available Luna and Terra tiers), Cursor Composer/agent workflows,
Zhipu GLM models and Moonshot Kimi models. Any '0xAlpha' system will be included only after its
provider and model identifier are verified. Composer and Composio-integrated workflows will be
labeled as product/orchestration conditions, not base models.

Experimental Design
 - Two tracks: (A) controlled API tests with the same user prompt and matched settings where
    supported; (B) native-product tests with default user-visible behavior.
 - A pilot suite of 24 tasks in six categories, three repeated runs per task and meaning-preserving
    prompt variants. At eight systems this gives 576 core observations.
 - Automatic checks for code/tests, exact-answer tasks and format compliance; blind human rubric
    scoring for open-ended work; LLM judging only as a secondary measure.
 - Randomized answer order, anonymized model labels, no model judging its own output, fixed rubric,
    version/date logging and bootstrap confidence intervals.
 - Primary result: cost and tokens per successful task. Secondary metrics: quality score, pass rate,
    factual error rate, p50/p95 latency, robustness, refusal precision and over-refusal rate.

               3. HARDWARE AND SOFTWARE REQUIREMENTS
Feasibility Study
Technical feasibility is high because most candidate systems are cloud-hosted and can be accessed
through official APIs or user interfaces. The benchmark runner, response logs and scoring scripts can
run on a standard laptop. Financial feasibility will be maintained through a small pilot, output-token
limits, cached inputs where permitted and a pre-declared spending cap. Operational feasibility is
supported by automated execution and scoring, followed by a manageable blind review sample. No
model training or high-end GPU is required.

Expected Outcomes
 - An open benchmark specification, reusable task set, scoring rubric and experiment manifest.

 - Per-task and per-category results with confidence intervals instead of one unexplained rank.

 - A token-quality-cost frontier and practical guidance for model selection, prompt optimization and
    guardrail calibration.

Limitations and Ethics
Results will be time-bound because models and products change. API and interface conditions may not
be perfectly equivalent, proprietary tokenizers or hidden prompts may be inaccessible, and human
