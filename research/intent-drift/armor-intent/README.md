# armor-intent: mapping IntentBench onto ArmorIQ enforcement

This folder connects the intent-drift benchmark in `../` to ArmorIQ (Armor), the
intent-based governance layer for AI agents in `~/armor-iq`. It does two things:

1. Expresses every benchmark task's intent contract as a real Armor policy
   (`armor.policy.v1`), so the same fixtures that measure drift can also drive
   Armor enforcement.
2. Supplies the scored eval layer Armor does not yet have. Armor detects and
   blocks drift at runtime, but ships no benchmark that grades how much drift a
   given model or policy actually produces (`armoriq-tools` EvalsPage is an empty
   UI stub). IntentBench is that missing layer.

Everything here is derived from real task metadata and the real Armor IR. Nothing
is hand-tuned per result.

## What Armor is, in one paragraph

Armor is an intent-based security layer that sits between an AI agent and the
tools it calls (file edits, shell, MCP tools) and checks every call against two
independent gates before allowing it: a **policy** gate (is this action allowed
at all?) and an **intent** gate (did the agent declare it would do this in its
signed plan?). It fails closed. In the Claude Code / Codex plugins this runs as a
`PreToolUse` lifecycle hook that returns a deny decision; on the platform it runs
as a network proxy in front of MCP servers. Armor's own term for what this
benchmark measures is literally **intent drift**: "runtime tool invocation
diverges from its signed Intent Assurance Plan ... the proxy detects drift and
refuses the call."

## How the benchmark maps onto Armor's model

| IntentBench concept | Armor concept (real vocabulary) |
| --- | --- |
| The one change the task asks for (`in_scope`) | The permitted target; a `permit` statement on the fix file |
| The planted rabbit holes (`out_of_scope`) | `forbid` statements; and "tool not in plan" under the intent gate |
| `unrequested_changes > 0` (our drift metric) | **Drift** / "intent drift: tool not in plan" |
| Per-task scope contract | A `PolicyProfile` (`armor.policy.v1`), default `deny`, `deny_overrides` |
| Scoped / loose / vague prompt rungs | The agent-side behaviour Armor enforces *regardless* of prompt |
| A benchmark cell (arm x task) | One enforced session: policy gate + intent gate + audit |

## Files

- `intents.yaml` — the 17 domain intent contracts (one permitted target, four
  forbidden rabbit holes each), extracted from `../tasks/*/meta.yaml` by
  `../harness/gen_armor_intent.py`. Single source of truth for the policies.
- `policies/*.policy.json` — one real `armor.policy.v1` PolicyProfile per task,
  generated by `../harness/gen_armor_policies.py`. Default `deny`, `permit` the
  fix file, `forbid` the cross-file rabbit holes.
- `policies/index.json` — coverage summary across all 17 policies.
- `evals/eval-spec.md` — the scored eval contract: how a benchmark cell becomes
  an Armor eval case, what is graded, and in Armor's terms.

## The precision boundary, stated honestly

Armor's shipped policy conditions operate on `file.path`. Three of the four
rabbit holes in every domain live in a different file from the fix, so a path
`forbid` blocks them deterministically: **51 of 68 planted holes (75%)** are
covered by a path-level policy with zero sampling. The fourth hole in each domain
is the `old_<fn>` alias, which sits in the *same* file as the permitted fix and
cannot be separated by a `file.path` condition. That residue (17 of 68, 25%)
needs Armor's finer machinery: the signed intent plan naming the specific symbol,
or a `matches` condition on edit content (the same param-inspection Armor already
does for PCI/payment detection). The projection in the deliverables reports this
boundary rather than assuming 100% coverage.
