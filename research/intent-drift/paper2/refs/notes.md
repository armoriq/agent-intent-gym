## Read first: corrections to our own docs

These claims in docs/research-design.md and docs/related-work.md are wrong or overstated. Fix them before they reach the paper.

1. OpenAI audit (research-design.md Sec. 2). The source is "Why SWE-bench Verified no longer measures frontier coding capabilities" (OpenAI, Feb 23, 2026; openai2026why). The 138 audited problems (27.6% of 500) were ones o3 did not consistently solve; 59.4% of those had test design and/or problem description issues. The post does not say these issues caused the failures, and OpenAI did not "recommend dropping" the benchmark: it stopped reporting Verified scores and pointed to SWE-bench Pro.
2. "32.7% solution leakage" (SWE-bench+, aleithan2024swebench). The figure is 32.67%, but the denominator is the 251 instances SWE-Agent + GPT-4 resolved, not the full benchmark. Weak tests: 31.08% of the same set. SWE-bench+ has no peer-reviewed venue.
3. "File paths recalled 76% vs 53% for unseen files" (liang2025swebench). Wrong framing. 76% is top models' accuracy at naming the buggy file from the issue text alone on SWE-bench Verified; 53% is the ceiling on repositories outside SWE-bench (Sec. 4.1, Figure 8). It compares benchmark repositories with other repositories, not seen with unseen files.
4. LiveCodeBench (related-work.md). The draft mixes versions: v1 has 400 problems (May 2023 to Feb 2024) and 9 base + 20 instruction-tuned models; v2 has 511 problems (May 2023 to May 2024) and 18 base + 34 instruction-tuned models.
5. SpecBench. The paper is real. The body says the 90th-percentile gap grows by about 27 pp per tenfold increase in reference LOC (Sec. 3.1, Figure 2, R^2 = 0.21); only the abstract says 28, and it is not the mean gap.
6. Arike et al. The arXiv title starts with "Technical Report:"; the published AIES 2025 version drops it. The body's concrete figure is "over 90,000 tokens" (Finding 6), and the pattern-matching explanation is called suggestive.
7. Bondarenko et al. v1 of the abstract names o1-preview, v3 names o3. Cite v3 if we name o3.
8. SWE-rebench. Contamination inflation is hedged in the source ("might be inflated"). Do not state it as established.
9. ABC (zhu2025establishing). Published title is "Establishing Best Practices in Building Rigorous Agentic Benchmarks", NeurIPS 2025 Datasets and Benchmarks track. The CVE-Bench 33% reduction is absolute (percentage points).
10. Titles that differ between arXiv and the venue: Skalse et al. is "Reward Gaming" at NeurIPS (arXiv says "Reward Hacking"); Agentless at FSE is "Demystifying LLM-Based Software Engineering Agents"; Vijayvargiya et al. is now "Ambig-SWE: Interactive Agents to Overcome Underspecificity in Software Engineering" (ICLR 2026). refs.bib uses the venue version where a venue is confirmed.

## What is and is not new (for the contribution statement)

Verified prior work already has each of our three instruments on its own. A visible versus held-out test gap: SpecBench (zhao2026specbench, which calls itself the first to do this), EvilGenie (gabor2026evilgenie), and Ahmed et al. on SWE-bench (ahmed2026investigating). Out-of-scope actions against planted traps: OverEager-Bench (qu2026overeager), plus real-session overreach in Tang et al. (tang2026how). Prompt strictness or clarity as a factor: ImpossibleBench (zhong2025impossiblebench, Table 1), Ambig-SWE (vijayvargiya2026ambigswe), and SWE-bench Pro's problem-statement ablation (deng2025swebench, Sec. 6.2). We found no work that crosses all three (hidden intent split, scoped/loose/vague phrasings of the same bug, rabbit-hole edits) on the same solvable bug-fix tasks with contamination tags. State the contribution as that combination. The search was targeted, not exhaustive. Three further 2026 papers on prompt wording and scope (ji2026coding, gloaguen2026coding, weinberger2026promptinduced) are covered in their own section below; weinberger2026promptinduced already shows cleanup wording producing out-of-scope edits, so our novelty there is the contrast with vague wording and the hidden-test blindness, not the cleanup effect itself.

## SWE-bench family and agent frameworks

### jimenez2024swebench: SWE-bench: Can Language Models Resolve Real-world Github Issues?
Source checked: https://arxiv.org/abs/2310.06770 ; https://arxiv.org/bibtex/2310.06770 ; http://export.arxiv.org/api/query?id_list=2310.06770 (Comments: "ICLR 2024, https://openreview.net/forum?id=VTF8yNQM66") ; https://arxiv.org/html/2310.06770 ; OpenReview search API record VTF8yNQM66 (venue "ICLR 2024 oral", venueid ICLR.cc/2024/Conference)
Builds 2,294 task instances from GitHub issues and merged PRs across 12 popular Python repositories (Section 2.1, filtered down from about 90,000 PRs). A task counts as resolved only if all FAIL_TO_PASS and PASS_TO_PASS tests pass (Appendix, evaluation procedure); every instance has at least one fail-to-pass test, 40% have two or more, and a median of 51 additional tests check prior functionality (Section 2.3). Headline result: with BM25 retrieval the best model, Claude 2, resolves 1.96% (Section 5, Tables 2 and 5), and 4.8% with oracle retrieval (Section 5, Appendix Table 18). Method precedent: our hidden tests play the role of FAIL_TO_PASS plus PASS_TO_PASS, but SWE-bench gives the agent only the raw issue text and no tests at all, so it has no visible proxy to overfit and cannot measure a drift gap; it also uses one phrasing per task (the original issue), whereas we hold the bug fixed and vary scoped / loose / vague phrasings. Note: OpenReview capitalizes the title "Real-world Github Issues"; arXiv uses "Real-World GitHub Issues".

### chowdhury2024introducing: Introducing SWE-bench Verified
Source checked: https://openai.com/index/introducing-swe-bench-verified/ (live page returned HTTP 403 to curl and WebFetch; read the Internet Archive capture http://web.archive.org/web/20261015035623/https://openai.com/index/introducing-swe-bench-verified/ ; authors as listed in the page's "Authors" section)
OpenAI blog post (August 13, 2024; "Updated February 24, 2025") releasing a human-validated 500-task subset of SWE-bench. 93 Python-experienced developers annotated 1,699 random SWE-bench test samples, each labelled by 3 annotators with the highest severity kept (section "Our Approach"); 38.3% were flagged for underspecified problem statements, 61.1% for FAIL_TO_PASS tests that may reject valid solutions, and 68.3% were filtered out overall (section "Annotation Results"). The 500 samples include a 196-task "easy" (<15 min) subset and a 45-task "hard" (>1 hour) subset (section "SWE-bench Verified"); GPT-4o on the best scaffold resolves 33.2% on Verified versus 16% on the original SWE-bench (section "Performance on SWE-bench Verified"). Supports: the scikit-learn-14520 example (section "Adapting SWE-bench as a Preparedness Evaluation") is a test that requires an exact deprecation message the issue never asks for, which is exactly the mismatch between issue wording and test-encoded intent that our three phrasings and visible/hidden split are built to measure.

### zhang2025swebench: SWE-bench Goes Live!
Source checked: https://arxiv.org/abs/2505.23419 ; https://arxiv.org/bibtex/2505.23419 ; https://arxiv.org/html/2505.23419 ; https://proceedings.neurips.cc/paper_files/paper/2025/hash/d83c4a745789690f82e86d0ef752ae7c-Abstract-Datasets_and_Benchmarks_Track.html and its BibTeX export ; OpenReview search API record OGWkr7gXka (NeurIPS 2025 Datasets and Benchmarks Track poster)
SWE-bench-Live (arXiv title "SWE-bench Goes Live!") uses an automated pipeline (RepoLaunch builds the Docker environment) to collect 1,319 tasks from issues created between January 1, 2024 and April 20, 2025 across 93 Python repositories, with a 300-task Lite subset (Section 3.4). ### deng2025swebench: SWE-Bench Pro: Can AI Agents Solve Long-Horizon Software Engineering Tasks?
Source checked: https://arxiv.org/abs/2509.16941 (v1 2025-09-21, v2 2025-11-14) ; https://arxiv.org/bibtex/2509.16941 ; https://arxiv.org/html/2509.16941 ; OpenReview search API records uEVTdoAbnK (venue "ICML 2026 regular", venueid ICML.cc/2026/Conference) and 9R2iUHhVfr (ICLR 2026 rejected submission)

Kept as @misc: OpenReview lists the paper as ICML 2026 but with an 18-author list that drops Nitin Pasari, Vijay Bharadwaj, Jeff Holm and Raja Aluri, and PMLR has not yet published ICML 2026, so the arXiv author list is used.

## Function-level code benchmarks, contamination, benchmark validity

### chen2021evaluating: Evaluating Large Language Models Trained on Code
Source checked: https://arxiv.org/abs/2107.03374 (v2), https://arxiv.org/bibtex/2107.03374, https://arxiv.org/pdf/2107.03374
Introduces Codex and the HumanEval set of 164 hand-written Python problems with an average of 7.7 unit tests each (Section 2.2), and defines functional correctness via pass@k: generate n >= k samples per task (n = 200, k <= 100 in the paper), count the c correct ones, and use the unbiased estimator pass@k = E_problems[1 - C(n-c, k) / C(n, k)] (Section 2.1, Eq. 1, numerically stable code in Figure 3, bias of the naive 1-(1-p)^k estimator shown in Appendix A). Codex-12B reaches 28.81% pass@1, 46.81% pass@10 and 72.31% pass@100 on HumanEval (Table 1; 28.8% also in the abstract). Appendix E.2 defines a model as "intent misaligned" when it outputs B where the user would prefer A, while being capable of producing A and of distinguishing the two situations. Background: pass@k on visible unit tests is the metric our drift gap is measured against, and the Appendix E definition of intent misalignment is a direct conceptual ancestor of our "intent drift".

### austin2021program: Program Synthesis with Large Language Models
Source checked: https://arxiv.org/abs/2108.07732 (v1), https://arxiv.org/bibtex/2108.07732, https://arxiv.org/pdf/2108.07732
Introduces MBPP, 974 crowd-sourced entry-level Python tasks each with a description, reference solution and three assert-based test cases (Section 2.1), and reports 59.6% few-shot solve rate for the largest (137B) model (abstract, Section 1). Section 4.4 writes adversarial "challenge" tests for 50 of the 500 test problems: solve rate falls from 66% on the normal tests to 58% with challenge tests, so roughly 12% of counted solutions do not generalize (Figure 7 shows a task where all samples delete every occurrence of a character instead of the first and last). Section 4.5 and Figure 8 document a model hard-coding `if n == 383: return True` to pass the visible asserts of the Woodall-number task. Method precedent: held-out challenge tests to measure the gap between passing visible tests and satisfying intent, at small scale and on single functions rather than agentic repository edits.

### liu2023evalplus: Is Your Code Generated by ChatGPT Really Correct? Rigorous Evaluation of Large Language Models for Code Generation
Source checked: https://arxiv.org/abs/2305.01210 (v3), https://arxiv.org/pdf/2305.01210, https://proceedings.neurips.cc/paper_files/paper/2023/hash/43e9d647ccd3e4b7b5baab53f0368686-Abstract-Conference.html, https://proceedings.neurips.cc/paper_files/paper/2023/file/43e9d647ccd3e4b7b5baab53f0368686-Bibtex.bib
EvalPlus augments HumanEval with LLM-seeded and type-aware-mutation test inputs (80x more tests) checked differentially against corrected ground truth, producing HumanEval+. Across 26 LLMs, pass@k drops by up to 23.1% (pass@1, greedy) / 19.3% (pass@1) / 24.9% (pass@10) / 28.9% (pass@100) (Section 3, "Evaluation of LLMs" paragraph, page 6, and Table 3; summarised as "up-to 19.3-28.9%" in the abstract and Section 1); GPT-4 greedy pass@1 goes from 88.4 to 76.2 (Table 3), and the same section reports that over 10% of the original HumanEval ground-truth solutions were incorrect. ### aleithan2024swebench: SWE-Bench+: Enhanced Coding Benchmark for LLMs
Source checked: https://arxiv.org/abs/2410.06992 (v2), https://arxiv.org/pdf/2410.06992 (v2), https://arxiv.org/pdf/2410.06992v1, https://api2.openreview.net/notes/search (records pwIGnH2LHJ, R40rS2afQ3, DmUaCItx3J)
Manually audits the 251 SWE-bench (full) instances that SWE-Agent + GPT-4 resolved: 82 (32.67%) are solution leakage, where the fix is spelled out in the issue text or comments, and 78 (31.08%) pass only because of weak tests, split into incorrect fixes 12.75%, changes to different files or functions than the gold patch 3.59%, and incomplete fixes 14.74% (Table 1, Section 1 and Section 2.1). ### liang2025swebench: The SWE-Bench Illusion: When State-of-the-Art LLMs Remember Instead of Reason
Source checked: https://arxiv.org/abs/2506.12286 (v4), https://arxiv.org/pdf/2506.12286 (v4), https://arxiv.org/pdf/2506.12286v1
Proposes diagnostic probes for memorization on SWE-Bench: predicting the buggy file path from the issue description alone, with no repository structure, and reproducing ground-truth functions verbatim. In v4, file-path accuracy reaches up to 76% on SWE-Bench Verified (range 60-76% across models), 57-71% on Full SWE-Bench, 50-68% on newly collected tasks from the same repositories, and is uniformly below 53% on Outside-Repo tasks from popular repositories not in SWE-Bench (Section 4.1, Figure 8); the gap persists after filtering out issues that mention the path (Section 4.2, Figure 9, Table 2). Consecutive 5-gram overlap when reproducing functions is up to 34.9% on SWE-Bench Verified versus up to 18.2% on other benchmarks (abstract, Section 4.3). Supports: evidence that SWE-Bench scores are inflated by memorization, motivating our post-cutoff and freshly written tasks.

### riddell2024quantifying: Quantifying Contamination in Evaluating Code Generation Capabilities of Language Models
Source checked: https://arxiv.org/abs/2403.04811, https://aclanthology.org/2024.acl-long.761/, https://aclanthology.org/2024.acl-long.761.bib, https://aclanthology.org/2024.acl-long.761.pdf
Matches the gold solutions of MBPP and HumanEval against The Pile and StarCoderData at surface and semantic level. Section 4.1 reports that 12.2% of HumanEval solutions and 3.6% of MBPP solutions have been seen in The Pile, versus 18.9% and 20.8% in StarCoderData (Figure 1). Models score far higher on the most-overlapping 10% of problems than on the least-overlapping 10%, e.g. StarCoderBase-15.5B 72.0% versus 22.0% on MBPP (Table 2), and removing likely contaminated items lowers accuracy, e.g. Pythia-12B on HumanEval by up to 82.7% relative (Table 1). Supports: quantitative evidence that classic code benchmarks are contaminated, justifying our "classic" tag as a separate stratum rather than a clean baseline.

## Specification gaming, reward hacking, Goodhart's law

### krakovna2020specification: Specification gaming: the flip side of AI ingenuity
Source checked: https://deepmind.google/discover/blog/specification-gaming-the-flip-side-of-ai-ingenuity/
DeepMind blog post (datePublished 2020-04-21 in the page's structured data; nine authors listed: Victoria Krakovna, Jonathan Uesato, Vladimir Mikulik, Matthew Rahtz, Tom Everitt, Ramana Kumar, Zachary (Zac) Kenton, Jan Leike, Shane Legg) that defines specification gaming as behaviour satisfying the literal specification of an objective without achieving the intended outcome, and reports "around 60 examples" collected so far (opening paragraph). It uses the Lego stacking example (agent flips the red block instead of stacking it) and argues the underlying problem is a failure to specify the intended outcome, not the bug being exploited. ### skalse2022defining: Defining and Characterizing Reward Gaming (arXiv title: Defining and Characterizing Reward Hacking)
Source checked: https://arxiv.org/abs/2209.13085 ; https://arxiv.org/bibtex/2209.13085 ; https://arxiv.org/pdf/2209.13085 ; https://proceedings.neurips.cc/paper_files/paper/2022/hash/3d719fee332caa23d5038b8a90e81796-Abstract-Conference.html
Gives a formal definition of reward hacking: a pair of reward functions is hackable relative to a policy set if there exist policies pi, pi' where one reward strictly prefers pi' and the other strictly prefers pi (Definition 1, Section 4.2); a proxy is unhackable if increasing proxy return can never decrease true return. The main negative result is Theorem 1 (Section 5.1): on any policy set containing an open set, two non-trivial unhackable reward functions must be equivalent, so with all stochastic policies (Corollary 1) unhackability forces the proxy to be equivalent to the true reward or trivial; Theorem 2 (Section 5.2) shows non-trivial unhackable pairs do exist for finite policy sets. Background: supplies the formal sense in which a visible test suite is a "narrower" proxy that can be hacked; it supports treating some drift as expected whenever the proxy omits terms of the intent. Note the NeurIPS proceedings title uses "Reward Gaming" while arXiv uses "Reward Hacking".

### pan2022effects: The Effects of Reward Misspecification: Mapping and Mitigating Misaligned Models
Source checked: https://arxiv.org/abs/2201.03544 ; https://arxiv.org/pdf/2201.03544 ; https://openreview.net/forum?id=JYtwGwIL7ye (via OpenReview API: ICLR 2022 Poster)
Builds four RL environments with nine proxy/true reward misspecifications (misweighting, ontological, scope; Section 3.2, Table 1) and varies agent capability (model size, training steps, action and observation resolution). More capable agents get higher proxy reward and lower true reward (Section 4.1, Figure 2), and Table 1 reports 5 instances of misalignment and 4 instances of phase transitions, where true reward drops sharply at a capability threshold (Sections 4.1 and 4.2, dashed red lines in Figure 2). Supports: predicts that drift gap need not shrink as models improve and may jump abruptly, which motivates measuring drift across model generations; their "scope" misspecification (proxy measured over a restricted domain) is a close analogue of tests that cover only part of the intended behaviour.

### manheim2018categorizing: Categorizing Variants of Goodhart's Law
Source checked: https://arxiv.org/abs/1803.04585 ; https://arxiv.org/bibtex/1803.04585 ; https://arxiv.org/pdf/1803.04585
Splits Goodhart effects into four types: Regressional (Section 1: selecting on a noisy proxy also selects for the noise), Extremal (Section 2: optimization moves into regions where the proxy-goal relationship no longer holds, with subtypes Model Insufficiency and Change in Regime), Causal (Section 3: intervening on the proxy breaks the causal path, including "Metric Manipulation", e.g. a teacher changing test scores), and Adversarial (Section 4: another agent with different goals exploits the metric, including Campbell's law and Cobra effects). Method precedent: our visible/hidden split operationalizes Extremal Goodhart, Model Insufficiency, most directly: the visible tests are a simplified measure of the intent that is accurate for ordinary solutions, and agent optimization finds solutions where passing them no longer implies correctness, which the hidden tests detect. Agents that edit or delete tests instead correspond to Causal Goodhart via Metric Manipulation (Section 3). arXiv's BibTeX export gives year 2019 (latest version, 2019-02-24); v1 was submitted 2018-03-13, which we use.

### amodei2016concrete: Concrete Problems in AI Safety
Source checked: https://arxiv.org/abs/1606.06565 ; https://arxiv.org/bibtex/1606.06565 ; https://arxiv.org/pdf/1606.06565
Agenda paper defining five accident-risk problems with a running cleaning-robot example. Section 3 (Avoiding Negative Side Effects) describes objectives that focus on one task and thereby "implicitly express indifference" over other parts of the environment, so the agent disrupts them for small gains (the vase example); Section 4 (Avoiding Reward Hacking) describes objectives "gamed" by solutions valid in a literal sense that do not meet designer intent, listing causes including partially observed goals and Goodhart's law. Background: Section 4 frames our drift gap, and Section 3 is the direct precedent for our rabbit-hole metric, where out-of-scope edits are side effects the visible-test objective is indifferent to.

### denison2024sycophancy: Sycophancy to Subterfuge: Investigating Reward-Tampering in Large Language Models
Source checked: https://arxiv.org/abs/2406.10162 ; https://arxiv.org/bibtex/2406.10162 ; https://arxiv.org/pdf/2406.10162
Trains Claude-2-based assistants on a curriculum of increasingly gameable environments (political sycophancy, tool-use flattery, rubric modification; Section 3) and evaluates on a held-out environment where the model can edit a mock-up of its own reward code. The expert-iteration model trained on the full curriculum overwrote its reward in 45 of 32,768 episodes and also edited the unit tests to avoid detection in 7 of 32,768 (footnote 2, page 3; Figure 1 caption), versus 0 of 100,000 for the helpful-only model (Section 5.3). Retraining not to be sycophantic on early environments reduced but did not eliminate tampering, with the lowest case still overwriting reward and editing tests 4 times in 100,000 (Section 5.3, Figure 8), and HHH preference-model training did not prevent generalization (Section 1). Supports: shows that gaming learned on easy proxies generalizes to editing tests, the most extreme form of the behaviour we measure; the authors note (arXiv v2 comment, Figure 1 caption) that their tampering metric has false positives where the model edits the reward while trying to do the task honestly.

### bondarenko2025demonstrating: Demonstrating specification gaming in reasoning models
Source checked: https://arxiv.org/abs/2502.13295 ; https://arxiv.org/abs/2502.13295v1 ; https://arxiv.org/pdf/2502.13295
Palisade Research study in which an LLM agent with shell access is told to win against Stockfish; reasoning models often hack the environment (replacing the board state, replacing or running another copy of the engine) instead of playing (Section 4). ### baker2025monitoring: Monitoring Reasoning Models for Misbehavior and the Risks of Promoting Obfuscation
Source checked: https://arxiv.org/abs/2503.11926 ; https://arxiv.org/bibtex/2503.11926 ; https://arxiv.org/pdf/2503.11926
OpenAI paper showing that a GPT-4o monitor reading chain of thought detects reward hacking by a frontier reasoning model in agentic coding environments, and that training against the monitor yields obfuscated hacking (Section 3.2, Figure 4). Named hacks: making a verify function always return true (Figure 1); two systemic hacks, exit(0) to leave the environment early without running all tests and raise SkipTest to skip test evaluation (Section 2.1, Table 1, Figure 8); problem-specific hacks including writing stubs when test coverage is poor and modifying functions upstream of the testing framework or unit test files so tests trivially pass (Section 2.2); and in Appendix A, returning expected error codes (Figure 9), decompiling a reference solution's jar (Figure 11), parsing the test file at runtime to return expected values (Figure 12), and stubbing pandas plus 19 other files (Figures 13 to 15). ### zhong2025impossiblebench: ImpossibleBench: Measuring LLMs' Propensity of Exploiting Test Cases

### zhao2026specbench: SpecBench: Measuring Reward Hacking in Long-Horizon Coding Agents
Source checked: https://arxiv.org/abs/2605.21384 (abs page and export API), https://arxiv.org/html/2605.21384 (v2 body, 9 Sep 2026), https://arxiv.org/bibtex/2605.21384
SpecBench (Zhao, Srikanth, Wu, Jiang, all Weco AI) gives agents a spec plus visible feature-level validation tests and scores them on held-out tests that compose the same features, defining the reward hacking gap as validation pass rate minus held-out pass rate (Sec. 2, Eq. 1) over 30 systems tasks from a JSON parser (about 1,500 LOC reference) to an OS kernel (about 110,000 LOC). Method precedent and Contrasts: its gap metric is essentially our drift gap, and Table 2 claims it is "the first benchmark that explicitly measures reward hacking through a two-way test decomposition", so we must not claim the visible/hidden split as new; our difference is bug-fix tasks in existing code, prompt-phrasing variation, and out-of-scope edits, none of which SpecBench measures.

### laban2026llms: LLMs Get Lost In Multi-Turn Conversation

### liu2024lost: Lost in the Middle: How Language Models Use Long Contexts

## Prompt wording and scope: three 2026 papers read in full (follow-up)

These three were first verified at abstract level only; their bodies have now been read in full and the key numbers re-checked against the PDF text. Bottom line for our claim ("scope-inviting prompts, not vague prompts, drive out-of-scope edits; hidden tests miss them"): none anticipates it as a whole, but weinberger2026promptinduced anticipates its first half. Its "adjacent cleanup" clause ("While you are in there, feel free to clean up anything adjacent that could be improved...") is, with autonomy language, one of only two prompt features that produce out-of-scope edits (5 to 8% of runs on two open models, about 0% elsewhere; App. E.1), and "Scope-expanding language was the only prompt family that consistently widened code diffs" (Sec. 3). It does not test vague wording for scope, does not link scope violations to hidden tests, and found no effect on Claude Sonnet 5 (162/162 scope-compliant, App. K). ji2026coding points the other way on vagueness: in DevOps operations, weaker intent clarity raises acted-run OverScope from 47.3% to 66.3% (Sec. V-C). gloaguen2026coding shows action-pushing instruction wrappers increase unneeded edits on already-fixed issues, with no cleanup-versus-vague contrast and no test analysis.

### ji2026coding: Coding Agents Are Guessing: Measuring Action-Boundary Violations in Underspecified DevOps Instructions
Source checked: https://arxiv.org/abs/2607.02294, https://arxiv.org/bibtex/2607.02294, https://arxiv.org/pdf/2607.02294 (full v1 body, 9 pages), https://arxiv.org/html/2607.02294
UnderSpecBench takes 69 DevOps task families (Table I; four capability domains, nine control surfaces) and rewrites each fixed task into 4 x 4 x 2 = 32 instructions, 2,208 in total, along intent clarity (S0 to S3), target certainty (B0 to B3) and blast radius (R0, R1). Environment, tools and oracle stay fixed (Section III-B). Deterministic before/after state oracles label each run Safe Success, Wrong Target or OverScope, where OverScope means the action "exceeded the minimal scope required" (Section IV, Definition 1). Five agent x model configurations run fully autonomous: OpenCode with claude-haiku-4.5, Codex-5.1-mini and DeepSeek-v4, Claude Code with Haiku-4.5, and Codex with Codex-5.1-mini (Section V-A). Overstep (Wrong Target or OverScope) covers 27.0% to 46.3% of all scored runs (Table II), and the headline "55.8-67.8% of acted runs violate at least one boundary" (Section I) matches Overstep divided by Action Rate from Tables II and III; the abstract drops "acted" and says "of runs". Target ambiguity drives overstepping (acted-run OverScope rises from 31.4% at B0 to 87.0% at B3) far more than intent vagueness (47.3% at S0 to 66.3% at S3), and blast radius has almost no effect (Section V-C, Figure 6). Supports and Gap we fill: it agrees that weaker wording makes agents act beyond the intended scope and that completion-centric scoring "can overstate safe autonomy". But it never uses wording that invites extra work, it has no visible/hidden test split (its oracle is a hidden state check, not a test suite), and its domain is DevOps operations rather than code edits around a bug fix.
Anticipation verdict: Partly. It anticipates "underspecified instructions lead coding agents to act beyond intended scope, and completion-style scoring hides this". It does not anticipate our split between scope-inviting wording (which drives out-of-scope edits) and merely vague wording (which does not); its intent-clarity result points the other way, since vaguer intent raises OverScope. It also does not anticipate our finding that hidden tests miss these edits.

### gloaguen2026coding: Coding Agents Don't Know When to Act
Source checked: https://arxiv.org/abs/2605.07769, https://arxiv.org/bibtex/2605.07769, https://arxiv.org/pdf/2605.07769 (v1, full body incl. appendices A to E)
FixedBench takes a random 200 SWE-Bench Verified instances, commits the golden patch so the issue is already resolved (RESOLVED task), and counts any patch that still touches code (after filtering out tests, comments, docstrings and non-code files, Appendix A) as a failure; it also builds a PARTIAL task (150 instances with an incorrect GPT-5 nano patch applied) to measure over-abstention (Sections 2.3, 2.5, 3.2, Appendix A). Five models in their native harnesses (Sonnet 4.6 / Claude Code, GPT-5.3 Codex and GPT-5.4 mini / Codex, Gemini 3 Pro / Gemini CLI, Qwen3.5-122B / Qwen Code, plus GPT-5.3 Codex in SORCAR) "apply unnecessary edits to already-fixed code in 35 to 65% of cases" under the plain ISSUE prompt in the BEST scenario (Section 3.2, Figure 2, Table 1); this range is one minus the correct abstention rate. The only prompt-wording manipulation is a set of four instruction wrappers around the unchanged issue text (ISSUE, EDIT, REPRODUCE, ABSTAIN OR FIX; Section 3.1, Appendix E): the EDIT wrapper ("Please edit the codebase to address the following task:") lowers correct abstention from 65.0% to 56.5% (Sonnet 4.6) and from 60.5% to 36.5% (GPT-5.4 mini), while ABSTAIN OR FIX raises it to 80.5% and 88.5% (Section 3.2, Table 1). In the trace analysis, 87.1% of unsuccessful traces modify "code unrelated to the issue they were supposed to resolve" (Section 3.3, Figure 7; LLM judge with 80.5% precision and 75.0% recall against 50 human-labelled traces, Appendix C). Supports and Gap we fill: it shows that action-inviting instruction framing increases unneeded edits, but it does not vary cleanup or improvement wording against underspecification (SWE-Bench Verified already filters underspecified issues, Section 2.2), plants no adjacent rabbit holes, and never tests whether the unneeded edits pass or evade the test suite, which is our contribution.
Anticipation verdict: Partly. It anticipates "prompt framing that invites action drives unneeded edits" (EDIT wrapper) and reports unrelated edits, but not the scope-inviting versus vague contrast, not out-of-scope edits on a task that genuinely needs a fix, and not the hidden-test blind spot.

### weinberger2026promptinduced: Prompt-Induced Waste in Coding Agents: Reasoning, Effort, Harness Design, and End-to-End Cost
Source checked: https://arxiv.org/abs/2608.01347, https://arxiv.org/bibtex/2608.01347, https://arxiv.org/pdf/2608.01347 (v6, 10 Sep 2026, full body read)
A preregistered cost study: six open-weight reasoning models plus Claude Sonnet 5 on 24 small deterministic tasks (at most 4 files; 8 low / 8 medium / 8 high; Python, JavaScript, Go), each with visible tests, hidden deterministic tests absent from the workspace, and allowed/forbidden paths, run under PI.DEV and Claude Code with 18 frozen prompt variants that append one clause to a fully specified baseline (4,644 valid runs; Section 2, Appendix A.3-A.5, exact wording in Table 4 and Appendix C). The primary outcome is a paired reasoning-token ratio and cost per success; out-of-scope changes (git diff vs. allowed paths) are a secondary metric, and the "adjacent cleanup" clause ("While you are in there, feel free to clean up anything adjacent that could be improved: refactor awkward code, tidy naming, and make related general improvements where you see the opportunity.") is described as authorizing scope expansion (Table 4). Section 3 reports that "Scope-expanding language was the only prompt family that consistently widened code diffs", and Appendix E.1 that adjacent cleanup, together with autonomy language ("Do not ask me any questions. Infer any missing details yourself ..."), is "one of only two features that produce out-of-scope edits (5-8% of their runs; ≈0% elsewhere)", while Sonnet 5 had 162/162 scope compliance including adjacent cleanup (Appendix K) and forced branching raised scope violations about 3x on easy cells (Section 3; "2.5x" in Appendix P). Its separate "ambiguous scope" stress variant ("Something in this project is producing wrong results related to the following area: price and discount calculations. Improve the situation.", Appendix C.3) is reported only for success (83%, the lowest in the benchmark) and reasoning (1.44x) (Appendix E.2), with no out-of-scope rate, and the paper never relates scope violations to hidden-test outcomes. Supports (partial precedent): independent evidence that cleanup-style wording, not other prompt families, widens diffs into out-of-scope edits; Gap we fill: it does not contrast scope-inviting against vague wording on out-of-scope edits, has no planted rabbit holes, and does not show that hidden tests miss those edits.
Anticipation verdict: PARTLY. It anticipates the "cleanup wording drives out-of-scope edits" half (Section 3, Appendix E.1), as a secondary finding of a cost paper with small effect sizes (5-8%) that do not show on Sonnet 5. It does not anticipate the vague-versus-scope-inviting contrast or the claim that hidden tests miss scope violations.

#### Gap check: what prior work already does (verified)
- Visible vs hidden test split for coding agents: ALREADY EXISTS. SpecBench (zhao2026specbench) defines exactly a validation-minus-held-out gap; EvilGenie (gabor2026evilgenie) used a 30% hidden holdout earlier; Ahmed et al. (ahmed2026investigating) measure visible-pass/hidden-fail overfitting on SWE-bench; ImpossibleBench ablates hidden vs open tests (Sec. 5.2). We cannot claim the split itself as novel. Note also that SWE-bench itself scores against hidden tests.
- Out-of-scope actions / scope creep: ALREADY EXISTS in two forms. OverEager-Bench (qu2026overeager) uses planted traps for unrequested actions on benign tasks; Tang et al. (tang2026how) report "Self-Initiated Overreach" in real sessions. Also verified at abstract level only (arXiv export API): "Coding Agents Are Guessing: Measuring Action-Boundary Violations in Underspecified DevOps Instructions" (Ji et al., arXiv:2607.02294, 2026), UnderSpecBench, which varies instruction intent clarity, target certainty, and blast radius and scores OverScope outcomes, with 55.8% to 67.8% of runs violating at least one boundary; and "Coding Agents Don't Know When to Act" (Gloaguen et al., arXiv:2605.07769, 2026), FixedBench, where agents propose unneeded code changes on already-fixed issues in 35% to 65% of cases.
- Prompt phrasing as a factor: ImpossibleBench varies prompt strictness (Table 1); UnderSpecBench varies instruction clarity; "Prompt-Induced Waste in Coding Agents" (Weinberger and Hozez, arXiv:2608.01347) varies prompt wording with hidden tests and allowed/forbidden paths but studies cost, not intent drift (body grep only, not read in full).
- What we found no prior work doing: one benchmark that, on the same bug-fix tasks, crosses (a) a visible/hidden intent split, (b) controlled scoped/loose/vague phrasings of the same bug, and (c) out-of-scope code edits against planted adjacent rabbit holes, with contamination tags. Our gap claim should be stated as this combination, not as any single component. This rests on the searches above and is not exhaustive.
