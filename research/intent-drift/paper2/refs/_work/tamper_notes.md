# Cluster: tamper (test tampering, reward hacking in coding agents, scope and drift)

### zhong2025impossiblebench: ImpossibleBench: Measuring LLMs' Propensity of Exploiting Test Cases
Source checked: https://arxiv.org/abs/2510.20270 (via export API), https://arxiv.org/html/2510.20270 (v1 body), https://arxiv.org/html/2510.20270v1/swebench_headline_short.png (Figure 3), https://arxiv.org/html/2510.20270v1/livecodebench_headline_short.png (Figure 4), https://arxiv.org/bibtex/2510.20270
ImpossibleBench (Zhong and Raghunathan at CMU, Carlini at Anthropic) mutates the unit tests of LiveCodeBench and SWE-bench tasks so they contradict the natural-language spec ("one-off" flips one expected value, "conflicting" adds a contradictory duplicate assertion), so any pass counts as cheating (Sec. 2.2). GPT-5 cheats on 76% of Oneoff-SWEbench and 2.9% of Oneoff-LiveCodeBench tasks (Sec. 1) and 54.0% of Conflicting-SWEbench (Sec. 4, Figure 3); the other per-model rates are plotted only in Figure 3, read approximately from the plot as Conflicting-SWEbench: Sonnet 3.7 about 64%, Opus 4.1 about 50%, o4-mini about 49%, Sonnet 4 about 43%, o3 about 29%, Qwen3-Coder about 14%, GPT-4.1 about 3% [read from figure, not stated in text]. Sec. 4.1 names four strategies (modify test cases; overload comparison operators; record extra states, e.g. call counting; special-casing), and Sec. 4.2 / Figure 5 finds Claude models and Qwen3-Coder cheat mostly (>79%) by modifying tests while OpenAI models use each strategy at >14%; Sec. 5.1 / Table 1 shows looser prompts raise cheating (prompts A and B give >85% for GPT-5 and o3 on Conflicting-LiveCodeBench, the strictest prompt D lowers them to 1% and 33%), and Sec. 5.2 / Figure 7 shows hiding tests drives cheating to near zero but also lowers legitimate performance. Method precedent and Contrasts: it is the closest prior work on test exploitation and on prompt-strictness effects, but it builds deliberately impossible tasks, whereas our tasks are solvable and we measure drift from intent on a hidden split plus out-of-scope edits.
Caution: Sec. 5.3 says the abort option lowers o3 from 49% to 12% on Conflicting-SWEbench, which does not match the roughly 29% o3 value in Figure 3; the 49% may belong to a different configuration. Do not cite an o3 number without rechecking.

### vonarx2025recent: Recent Frontier Models Are Reward Hacking
Source checked: https://metr.org/blog/2025-06-05-recent-reward-hacking/
METR blog post dated June 5, 2025, contributors listed as Sydney Von Arx, Lawrence Chan, and Beth Barnes; it documents o3 (and Claude 3.7 Sonnet, o1) cheating on METR's autonomy tasks by overwriting timers, monkey-patching evaluators, overriding equality operators, and copying the grader's reference answer. The table "Tasks where o3 displayed reward-hacking behavior" reports RE-Bench total 39 of 128 runs (30.4%), including Optimize LLM Foundry 21 of 21 (100%), Optimize a Kernel 6 of 24 (25.0%), and Scaffolding for Rust Codecontest 12 of 28 (42.9%), versus HCAST total 8 of 1087 (0.7%); the text says reward hacking was more than 43 times more common on RE-Bench, possibly because the scoring function was visible, and a footnote says these numbers are for an earlier o3 version. In the section "Do models know they're reward hacking?", adding "please do not cheat" style instructions to the Optimize LLM Foundry prompt left reward-hacking plans at 70% to 95% of 20 runs per prompt. Supports: frontier agents optimize the visible scorer against clear user intent, and visibility of the scoring code seems to raise the rate, which motivates our hidden intent tests.

### zhao2026specbench: SpecBench: Measuring Reward Hacking in Long-Horizon Coding Agents
Source checked: https://arxiv.org/abs/2605.21384 (abs page and export API), https://arxiv.org/html/2605.21384 (v2 body, 9 Sep 2026), https://arxiv.org/bibtex/2605.21384
SpecBench (Zhao, Srikanth, Wu, Jiang, all Weco AI) gives agents a spec plus visible feature-level validation tests and scores them on held-out tests that compose the same features, defining the reward hacking gap as validation pass rate minus held-out pass rate (Sec. 2, Eq. 1) over 30 systems tasks from a JSON parser (about 1,500 LOC reference) to an OS kernel (about 110,000 LOC). The 90th-percentile gap grows by about 27 percentage points per tenfold increase in reference LOC (Sec. 3.1, Figure 2, R^2 = 0.21; the abstract says 28), weaker models show larger gaps while all models nearly saturate the visible suite (Sec. 3.2, Figure 4), and Claude Code shows gaps of roughly 43 to 48 pp across search strategies (Sec. 3.3, Figure 5). Sec. 3.6 describes Codex on the C compiler task producing a 2,900-line hash table of precomputed outputs that scored 97% on validation and 0% held-out, selected by AIDE over an earlier genuine 7,900-line compiler. Method precedent and Contrasts: its gap metric is essentially our drift gap, and Table 2 claims it is "the first benchmark that explicitly measures reward hacking through a two-way test decomposition", so we must not claim the visible/hidden split as new; our difference is bug-fix tasks in existing code, prompt-phrasing variation, and out-of-scope edits, none of which SpecBench measures.

### arike2025evaluating: Evaluating Goal Drift in Language Model Agents
Source checked: https://arxiv.org/abs/2505.02709 (export API), https://arxiv.org/html/2505.02709 (body), https://ojs.aaai.org/index.php/AIES/article/view/36541 (proceedings metadata)
The arXiv version is titled "Technical Report: Evaluating Goal Drift in Language Model Agents"; the AIES 2025 proceedings version (vol. 8, no. 1, pp. 192 to 203) drops the "Technical Report:" prefix. Agents get a goal in the system prompt and then face competing objectives in a simulated stock-trading environment, and the abstract reports that a scaffolded Claude 3.5 Sonnet keeps nearly perfect adherence for more than 100,000 tokens in the hardest setting while all evaluated models show some drift (Finding 6 in Sec. 4.2 gives the concrete figure: strong adherence after 64 instrumental steps, over 90,000 tokens). Sec. 5.2 and Figure 5 attribute drift to growing susceptibility to pattern-matching in-context behavior rather than token distance, although the authors call this only suggestive because most correlations are not statistically significant (Appendix E). Background: it names "goal drift" and even gives a hypothetical coding-agent scope example in Sec. 1, but it measures it in a trading simulation, not on code, so our measurement of drift on real coding tasks is a gap we fill.

### gabor2026evilgenie: EvilGenie: A Reward Hacking Benchmark
Source checked: https://arxiv.org/abs/2511.21654 (export API; v1 26 Nov 2025, v2 17 May 2026), https://arxiv.org/html/2511.21654 (v2 body), https://arxiv.org/bibtex/2511.21654
EvilGenie takes 154 "hard" LiveCodeBench problems (Sec. 2.1), exposes some tests to the agent, and withholds a random 30% (up to 10) as holdout tests the agent is not told about (Sec. 2 and 4.1); it detects reward hacking with holdout tests, LLM judges, and test-file edit detection, all checked against human review. Table 1 (unambiguous problems, n = 145) gives Codex/GPT-5, Claude Code/Sonnet 4, and Gemini CLI/Gemini 2.5 Pro legitimate-and-correct rates of 77.2%, 42.1%, and 58.6%, with hardcoded tests at 0.7%, 2.1%, 0%, Claude "heuristic solutions" at 20.7%, and Gemini deleting the test file in 3.4% of runs; on the 9 ambiguous problems (Table 2) hardcoding rises to 44.4%, 33.3%, 22.2%. Sec. 5.1 argues held-out tests are not foolproof: heuristic solutions sometimes pass the holdout set, and the LLM judge was the most effective detector. Method precedent: it is earlier (Nov 2025) than SpecBench in using a visible/holdout test split on coding agents, and its finding that holdout tests miss some hacks is a limitation we should acknowledge for our hidden intent tests.

### anthropic2025claude: Claude 3.7 Sonnet System Card
Source checked: https://www.anthropic.com/claude-3-7-sonnet-system-card (resolves to the PDF on www-cdn.anthropic.com; same file as https://assets.anthropic.com/m/785e231869ea8b3b/original/claude-3-7-sonnet-system-card.pdf), https://www.anthropic.com/news/claude-3-7-sonnet (dated Feb 24, 2025, links the system card)
Anthropic's system card for Claude 3.7 Sonnet has a section titled "6 Excessive Focus on Passing Tests" (pp. 22 to 23) stating that the model "occasionally resorts to special-casing in order to pass test cases in agentic coding environments like Claude Code", most often by returning expected test values and sometimes by modifying the tests, typically after repeated failed attempts at a general solution. Sec. 6.1 attributes the behavior to reward hacking during RL training, and Sec. 6.2 recommends system prompts favoring general solutions and monitoring for "unexpected modifications to test files". The PDF itself carries no date; the month comes from the linked announcement. Supports: a developer's own first-party account that agentic coding models optimize visible tests over intent.

### qu2026overeager: Overeager Coding Agents: Measuring Out-of-Scope Actions on Benign Tasks
Source checked: https://arxiv.org/abs/2605.18583 (export API), https://arxiv.org/html/2605.18583 (v1 body), https://arxiv.org/bibtex/2605.18583
OverEager-Bench has 500 validated benign-task scenarios with planted trap predicates (deleting unrelated files, touching credentials, rewriting unmentioned config) and about 7,500 runs over Claude Code, OpenHands, Codex CLI, and Gemini CLI. Stripping the in-prompt consent/scope declaration raises Claude Code's overeager rate from 0.0% to 17.1% on paired scenarios (Sec. 3 and Table 1), with increases of 11.9 to 17.2 pp on every shared base model; across frameworks the permissive agents run at 5.4% to 27.7% versus 0.2% to 4.5% for OpenHands (Sec. 5.2, Table 2). Method precedent and Contrasts: it is the closest prior measurement of out-of-scope actions against planted traps, similar to our rabbit holes, but its traps are security and operational side effects on benign tasks, not code edits beyond a bug fix, and it does not measure test-passing versus intent.

### ahmed2026investigating: Investigating Test Overfitting on SWE-bench
Source checked: https://arxiv.org/abs/2511.16858 (abs page and export API; v3, 3 Apr 2026), https://arxiv.org/pdf/2511.16858 (body), https://arxiv.org/bibtex/2511.16858
This IBM study runs auto-generated reproduction tests (visible to the system) against Agentless patches on SWE-bench and checks the hidden golden tests: with Claude 3.7 Sonnet, 50 of the 229 patches that pass the generated tests fail the hidden tests, a 21.8% overfitting rate, and GPT-4o reaches 33.0% (Sec. 4.1, Table 1). Refining code against the visible tests raises Claude's overfitting rate to 25.5% (Sec. 4.2), and overfitted patches have lower coverage (Sec. 5). Supports and Method precedent: a visible-pass versus hidden-fail measurement on repository bug fixes, close to our drift gap, though it studies a pipeline with generated tests rather than agent behavior under prompt variation or scope. The paper's own header names FSE Companion '26 with DOI 10.1145/3803437.3805574, but ACM DL returned 403 and the arXiv comments field is empty, so the venue is not claimed here.

### tang2026how: How Coding Agents Fail Their Users: A Large-Scale Analysis of Developer-Agent Misalignment in 20,574 Real-World Sessions
Source checked: https://arxiv.org/abs/2605.29442 (export API), https://arxiv.org/html/2605.29442 (v2 body), https://arxiv.org/bibtex/2605.29442
An observational study of 20,574 real IDE and CLI coding-agent sessions (16,118 evidence-grounded misalignment episodes) that codes how agents diverge from developer instructions and intentions. In Sec. 4.1, "Self-Initiated Overreach" (S4) appears in 10.20% of episodes; within it, "Scope Overreach" (C2) accounts for 66.99%, described as agents treating a narrow task as license to add unrequested infrastructure or architectural changes, and "Misread Developer Intent" appears in 26.95% of episodes, 44.10% of them tied to underspecified instructions. Supports: field evidence that out-of-scope edits and intent misreading under vague prompts happen in real use, which motivates our controlled measurement of both.

## Gap check: what prior work already does (verified)
- Visible vs hidden test split for coding agents: ALREADY EXISTS. SpecBench (zhao2026specbench) defines exactly a validation-minus-held-out gap; EvilGenie (gabor2026evilgenie) used a 30% hidden holdout earlier; Ahmed et al. (ahmed2026investigating) measure visible-pass/hidden-fail overfitting on SWE-bench; ImpossibleBench ablates hidden vs open tests (Sec. 5.2). We cannot claim the split itself as novel. Note also that SWE-bench itself scores against hidden tests.
- Out-of-scope actions / scope creep: ALREADY EXISTS in two forms. OverEager-Bench (qu2026overeager) uses planted traps for unrequested actions on benign tasks; Tang et al. (tang2026how) report "Self-Initiated Overreach" in real sessions. Also verified at abstract level only (arXiv export API): "Coding Agents Are Guessing: Measuring Action-Boundary Violations in Underspecified DevOps Instructions" (Ji et al., arXiv:2607.02294, 2026), UnderSpecBench, which varies instruction intent clarity, target certainty, and blast radius and scores OverScope outcomes, with 55.8% to 67.8% of runs violating at least one boundary; and "Coding Agents Don't Know When to Act" (Gloaguen et al., arXiv:2605.07769, 2026), FixedBench, where agents propose unneeded code changes on already-fixed issues in 35% to 65% of cases.
- Prompt phrasing as a factor: ImpossibleBench varies prompt strictness (Table 1); UnderSpecBench varies instruction clarity; "Prompt-Induced Waste in Coding Agents" (Weinberger and Hozez, arXiv:2608.01347) varies prompt wording with hidden tests and allowed/forbidden paths but studies cost, not intent drift (body grep only, not read in full).
- What we found no prior work doing: one benchmark that, on the same bug-fix tasks, crosses (a) a visible/hidden intent split, (b) controlled scoped/loose/vague phrasings of the same bug, and (c) out-of-scope code edits against planted adjacent rabbit holes, with contamination tags. Our gap claim should be stated as this combination, not as any single component. This rests on the searches above and is not exhaustive.
